EnduranceTestGUI User Manual

1What this tool does

EnduranceTestGUI is an endurance-testing tool that keeps sending random clicks, drags, key input, scrolling, shortcuts, and window operations to a target GUI application, within "operation regions" you define beforehand. It automates the kind of check that's tedious to do by hand: "does anything break if a button is pressed hundreds or thousands of times?"

A particular focus is making it possible to trace back what caused a problem after it happens. When the target app crashes, the tool automatically saves:

  • A dialog and log entry naming which step was running when it detected the crash
  • A screenshot of the screen at that moment, plus a recording of the last few seconds leading up to it
  • A full test-settings snapshot, including the RNG seed used, so the run can be reproduced
  • The location of the OS's own crash dump / diagnostic log, when available

See Crash detection & re-testing for details.

2Prerequisites & required permissions

macOS

Grant EnduranceTestGUI access under System Settings → Privacy & Security → Accessibility. If it isn't granted, a dialog prompting for permission appears when you try to start a run.

Also grant EnduranceTestGUI access under System Settings → Privacy & Security → Screen Recording. Without it, the screen capture used as the background of the operation-region selection screen (the semi-transparent overlay) can't be taken, so the whole screen appears painted solid black, making other apps look like they've vanished (nothing about the other apps has actually changed). The ① panel also shows this permission's status, with a button to open the relevant Settings pane directly if it isn't granted.

Launching from a terminal
Launching directly from a terminal app can cause the Accessibility permission check to be delegated to the terminal app itself instead of EnduranceTestGUI. Double-clicking EnduranceTestGUI.app directly in Finder is the reliable way to launch it.

Linux

No special permission is needed for sending input itself (it works as long as it can reach the X server). Only the right-click context-menu item-selection feature requires the target app's toolkit to support AT-SPI accessibility. Wayland is not supported (X11, or an X11 app running under XWayland, only).

Administrator (root) privileges are not required
When both the target app and EnduranceTestGUI are launched under a normal user account, every feature has been confirmed to work correctly without root.

3Screen layout

The window is divided into three vertical sections.

  • ① Target Selection (top): choosing the app under test, registering operation regions, and timing/limits settings
  • ② Steps (middle): the order of the actions to run. Each step's region, action types, count, and detailed parameters are all configured together in a dialog opened by double-clicking (or "Edit...") its row in the list
  • Run controls / Log (bottom): start/stop buttons, run status, and the log

4① Selecting the target app

Choose the window you want to test from the "Target" dropdown. If it doesn't appear in the list, click "Update" to re-scan. Once selected, whether EnduranceTestGUI has permission to operate that app is shown in green (granted) or red (not granted); if not granted, "Open Permission Settings" opens the relevant OS settings screen. Below that, macOS's Screen Recording permission status is shown the same way (always "granted" on Linux). Without it, the operation-region selection screen's background appears solid black, making other apps look invisible, so use "Open Screen Recording Settings" if it shows red.

Setting a path in "Target app auto-launch command (optional)" lets you try launching it manually at any time with "Launch now", and is also used by the continuous-run features described in "⑧ Starting and stopping the test". Checking "Launch the target tool with this command before starting" makes "▶ Start" launch the target app with this command first, wait for it to appear, and only then begin the startup setup and step sequence (the auto-launch command must be set when this is checked). Setting "Extra wait after target launch is detected" above 0 seconds waits that many extra seconds, after the target tool's window is detected, before actually starting the test. Use this for a tool that isn't ready to receive input right at launch, where starting immediately would otherwise fail the safety check (applies to continuous run, the automatic-relaunch wait, and the option above alike).

"Save current window size" records the size of the currently selected target window (just one at a time; it's also saved in the preset JSON, so it survives restarting the app). "Restore saved size" changes the currently selected target window to that saved size. If the requested size is smaller than the target app's own layout minimum, the actual size it ends up with may be rounded up. Likewise, "Save current window position" / "Restore saved position" save and restore the target window's on-screen position, one value at a time. Checking "Apply the saved window position/size on each continuous-run relaunch" automatically applies whichever of the saved size/position are set every time the target app is (re)launched and detected, before the run starts (applies alike to 連続実行's kill-then-relaunch cycle, the auto/manual relaunch wait for "continuous run count", and the "launch before starting" option).

About operation regions
The "Operation Regions" list lets you register named rectangular areas of the screen. Clicking "Add..." switches into rectangle-drawing mode without darkening the screen or overlaying any hint text -- once the mouse cursor turns into a crosshair, drag to draw a rectangle (multiple allowed; areas to exclude can be specified separately too). This works the same way even with multiple displays of different sizes or aspect ratios. When creating a step, choosing one of these registered regions instead of "the entire target GUI area" limits random actions to just that part of the screen. Enabling "Follow target window movement" (on by default for newly created regions) keeps the region moving together with the target window if it's repositioned while the test runs. Re-editing an already-following region without redrawing its rectangles keeps its original reference position, too.

Clicking "Show All Operation Regions" highlights every currently registered operation region on screen at once, each with its own name label (no need to check them one at a time). Clicking it again (the button then reads "Hide") -- or clicking it with no operation regions registered -- shows a guidance message instead. This highlight is automatically hidden whenever you "Add...", "Edit...", or delete an entry in the list, and also automatically hides itself after it's been shown for about 12 seconds (a safety net for window managers where the main window can become hard to interact with while an always-on-top highlight is showing).

Instead of drawing a rectangle, you can also register an operation region by choosing "Target a widget on screen". If the target app is built with a toolkit such as Qt and exposes an accessibility API (macOS Accessibility API / Linux AT-SPI), you can specify a button, menu item, or other widget by name, and it keeps being found even if the target app's layout shifts somewhat (see the box below for details).

Named objects (targeting an on-screen widget by name)

Choosing "Target a widget on screen" and clicking "Pick object..." switches the screen into picking mode. As you hover over buttons, menu items, and other widgets in the target app, a green box and the widget's role and name appear right there, so click while the widget you want is highlighted. If more than one widget on screen shares the same role and name, which "occurrence" you picked is determined automatically from the point you actually clicked, shown as e.g. "Targeting: push button "Save" (2nd match)".

A region registered this way can be referenced from a step exactly like a rectangle-based one, and existing actions -- click, drag, key input, scroll -- all work the same way. Since it follows the widget itself rather than fixed coordinates, it keeps pointing at the same widget even if the window's size or layout shifts somewhat. Checking "For click actions, run this widget's default action directly instead of using coordinates" makes a click invoke the widget's own default action (press for a button, toggle for a checkbox, etc.) through the accessibility API directly, instead of clicking a screen coordinate. "Re-resolve interval" controls how often the widget's position is looked up again while the same region keeps being used (the default, "only when entering a new step", looks it up once and reuses the result afterward, so even fast repeated actions see essentially no performance cost).

If the target app itself doesn't support the accessibility API, or you simply don't want to use it, check "Disable accessibility-API-based actions (context menu selection, dialog button press, named objects) for speed" in the ⑦ Timing & Limits panel. Enabling it stops any accessibility API calls altogether -- not just for steps that reference a named object, but for context menu selection and dialog button press as well.

Besides drawing a rectangle or targeting an on-screen widget, there's a third way to register an operation region: "Specify as Point Sequence (Sweep)". This is the same mechanism as the step-level "Point Sequence (Sweep)" described below (see "⑤ ② Building the steps") -- points evenly spaced along a path, visited in order, wrapping back to the first point once the path's end is reached -- but registered by name as an operation region itself rather than per step. Once registered, the same sweep point sequence can be referenced by name from multiple steps, without having to re-specify it for each one. Register it by clicking "Add Point..." repeatedly, picking points on screen in order to build up the path: a start, any number of midpoints, then an end ("Remove Selection" deletes any entry from the list). At least 2 points (a start and an end) are required, and any number of midpoints may sit between them. Points evenly spaced "Interval (px)" apart are generated along the path connecting the start, midpoints, and end in order, and visited in that sequence; "Random Offset (px)" works the same as for any other point sequence (sweep). When a step references a sweep-type region, that region's own point sequence is always used, regardless of that step's own "How to Pick the Operation Position" setting.

5Startup setup (running login etc. automatically, once)

Some target apps require a fixed sequence of operations right after launch -- logging in, an initial-setup dialog -- before endurance testing by random actions can begin. Registering a sequence of actions in ①'s "Startup Setup" list runs them once, in order, right after the target app is confirmed running and before ②'s random actions begin.

1Clicking "Add..." opens a dialog for configuring one action. Choose a "Type": Click, Double-click, Right-click, Drag, Text Input, Key Input, Wait, Wheel Scroll, or Select Menu Item. "Wheel Scroll" takes a position, direction (up/down/left/right), and amount. "Select Menu Item" takes the right-click position and always selects the same one item from the menu it opens, specified either by item name or by position from the top (if the target app's menu contents vary from run to run and the specified item isn't found, the whole setup sequence isn't failed — the menu is just closed instead). The existing "Right-click" type always just dismisses whatever menu it opens, without selecting anything.

2For click-family actions and Drag, clicking "Select Position..." covers the whole screen in a translucent overlay -- just click the spot on the target app you want (no need to type coordinates by hand). The position is stored relative to the target window's top-left corner, so it stays correct even if the window has moved by the next run. Once picked, a small marker stays visible on screen at that position for as long as this dialog stays open (for Drag, both the start and end markers are shown, connected by a line), so you can confirm at a glance that the right spot was picked.

3The optional "Description" field (e.g. "Username field") makes entries easier to tell apart in ①'s list.

4Clicking "OK" adds it to the list. Use "↑ Move Up"/"↓ Move Down" to reorder, "Edit..." to change an entry, or "Delete" to remove one. "Clear All" empties the whole list immediately, with no confirmation prompt.

Passwords and other sensitive text can be entered too
The "Text Input" type can be used for passwords and other sensitive text, but the content you type is never written to the run log, the full log file, or the diagnostic record saved on an abnormal stop (only the character count is recorded).

Checking "Only run on the first run of consecutive auto-execution (① batch)" makes the startup setup skip every automatic restart after the first one when you set ①'s "Batch run count" to 2 or more. Use this for something that only needs to happen once, like a license-agreement dialog that only appears the first time the app launches.

"● Record..." lets you build a whole startup setup sequence by actually performing it yourself, instead of adding entries one at a time. Clicking it shows a recording indicator panel in the top-right corner; while it's up, any mouse clicks, drags, or keyboard input you perform are appended to this list as you go, until you press Escape. This isn't limited to the target app's own window -- operating a dialog the target app opens (e.g. a confirmation dialog that appears after choosing a right-click menu item) is recorded the same way. Consecutive plain characters you type are recorded together as a single "Text Input" entry; Tab, Enter, arrow keys, etc. are each recorded as their own "Key Input" entry (a recorded click is always saved as a plain "Click" -- if you meant a double-click, change its type afterward via "Edit..."). Consecutive wheel notches are likewise coalesced into a single "Scroll" entry. If a left click right after a right click can be identified as picking an item from the menu that right-click opened, the two are recorded together as a single "Menu select" entry; when it can't be identified, they're recorded separately as an ordinary "Right Click" and "Click" instead. The real time that elapsed between recorded actions (except before the first one) is also automatically inserted into the list as a "Wait" entry, so replaying the sequence (e.g. via "▶ Test Startup Setup") reproduces roughly the same pacing you recorded it at (an inserted wait is an ordinary setup action too, so you can adjust its duration or delete it via "Edit..." like any other entry). Recording ends when you press Escape, or click "■ Stop Recording" on the indicator panel.

"▶ Test Startup Setup" runs just this list's setup against the target window selected in ①, so you can check it actually works. It doesn't run ②'s step configuration at all, so ② doesn't need to be set up yet. The run stops automatically once it finishes, and the status area shows "Startup setup verification completed". Clicking it with no setup actions configured shows an error dialog instead.

6② Creating steps (including action parameters)

A test is made up of one or more "steps" that run in order, repeating.

1Clicking "Add..." opens this step's settings dialog. First choose which region it will operate on: either "Entire target GUI area (auto-follows)" or one of the named operation regions registered in ①.

2Clicking "OK" adds the step to the list and selects it automatically. To change its settings later, either double-click its row in the list, or select it and click "Edit..." — either way reopens the same dialog. The shared initial values (defaults) used for newly created steps can be edited at any time via the "Default" button in ②'s header row, even with no step selected.

Steps can be reordered within the list with "Move Up"/"Move Down", or multi-selected and combined into a single group with "Group" (members within a group are picked at random according to their weight). Multi-selecting and using "Task" combines steps the same way, but unlike a group, a task always runs every combined step exactly once, in the order they were added, and the whole run counts as a single "run count" — use this when you have a sequence of actions that must not be randomly reordered. For either a group or a task, selecting it and pressing "Ungroup"/"Untask" splits it back into its original individual steps. "Add Wait..." lets you insert a "wait step" that does nothing for a specified number of milliseconds.

The step settings dialog's "How to Pick the Operation Position" lets you choose "Point Sequence (Sweep)" instead of the default "Random" (a fresh random point within the operating region every time). Pick two points with "Select Start Position..."/"Select End Position...", and the step cycles through points evenly spaced "Interval (px)" apart between them, one per action (wrapping back to the start once it reaches the end). This is for when you want to click your way up (or across) an area at a steady interval without having to hand-build a separate named region for every row — one step handles it. Setting "Random Offset (px)" above 0 adds a random up/down/left/right offset within that range each time a point is actually operated on, so it isn't the exact same pixel every single pass.

The region-selection dialog shown when adding or editing a task's actions also offers "Target a newly appeared window (dialog, etc.) (auto-detected)". An action using this option operates on whichever window newly appeared besides the target app's main window — e.g. a confirmation dialog opened by a preceding action's context-menu selection — instead of any of the usual named/whole-window regions. If no such window has appeared yet when it's this action's turn to run, it automatically waits until one does. For this "target a newly appeared window" task member, the detailed action settings also offer a "Press dialog button" action type. Register a list of candidate button names (e.g. "OK", "Yes") ahead of time, and at run time it searches that dialog for whichever of those names is actually present and clicks it (the same mechanism as context-menu item selection). If none of the candidates can be found, that attempt is skipped and retried on the next opportunity.

7Timing / limits & automatic anomaly recording

The "Timing / Limits" area of panel ① sets the interval between actions (ms, or actions/sec), the max action count, max run time, and repeat count for the whole step sequence (all three are required — unlimited isn't an option), the RNG seed, and more. Scrolling down reveals the following additional settings.

If you click "▶ Start" with a debugger attached but forgot to turn on "Debug mode", a "Debugger attachment detected" confirmation dialog appears before the run starts (continuous-run and CLI/headless runs have no one to confirm with, so they just log a warning and continue). If you proceed anyway, the same warning is also logged once during the run.

8Starting and stopping a run

Once configured, click "▶ Start" to begin the run. While it's running, an always-on-top floating panel appears in the upper right (showing the action count and a "■ Stop (STOP)" button), so you can stop it immediately even if focus has moved to the target app. "‖ Pause" lets you pause and resume as well.

Setting "Repeat count" to 2 or more and clicking "▶ Start" automatically begins the next run (waiting for the target app to relaunch) each time one finishes, repeating that many times. If the target app is still alive when a run ends it's reused as-is; if it has gone, the next run starts once the auto-launch command (①) restarts it, or once a manual relaunch is detected. Separately, the "⟳ Continuous run" button always terminates the target app first — whether or not it's currently running — before launching a fresh instance and running the startup setup and step sequence, repeating that kill-then-relaunch cycle for "Repeat count" cycles. Use it when you want every run to start from a genuinely clean instance (the auto-launch command in ① is required for this button). Either mode can be interrupted at any time with "■ Stop".

For each action, the log records its coordinates, the coordinates relative to the target window, and (when available) the name of the UI widget that was clicked. The full log is also written incrementally to a file under ~/Documents/EnduranceTestGUI_Logs/, so even after older lines scroll out of the on-screen display (capped at the most recent 5000 lines), the complete history remains available afterward.

A run stops automatically when any of the following happens:

  • The max action count, max run time, or sequence repeat count limit is reached
  • The user presses "■ Stop"
  • A crash or the disappearance of the target app's window is detected (see next section)
  • An action was about to land on something other than the target app (a fail-closed safety stop)
  • The target app stops responding (hang detection, Linux only)

Running from a terminal without opening the GUI (CLI/headless mode): Given a preset JSON saved with "Save test settings...", running EnduranceTestGUI --run <preset.json> [--repeat N] in a terminal runs the same test with no window shown at all. It behaves exactly like the "⟳ Continuous run" button: it terminates the target app, launches it fresh with the launch command (which must be saved in the preset), and repeats that cycle --repeat times (default 1). All progress, action logs, and the run summary are printed to stdout, and the process exits automatically once every repeat has finished (or once an error makes continuing impossible). The exit code is 1 if any run was anomalous (e.g. a crash) and 0 otherwise, so a shell script or CI pipeline can check success directly.

9Continuous recording & animation export

The "● Record" button in the run-control row is independent of "▶ Start" / "■ Stop". Regardless of whether a test is currently running, pressing it immediately starts capturing the target window as a sequence of numbered PNG frames at a 0.5 second interval, and keeps capturing until you press it again ("■ Stop recording"). You can use it to record manual operation of the target app, to record while an endurance run is in progress, or to record straight across both.

How this differs from "Save a recording of the last few seconds on an abnormal stop" in ⑦
The recording feature under ⑦ Timing / limits only ever kicks in automatically, replaying roughly the last 10 seconds leading up to a crash or other abnormal stop; it only works while a test is running, and it can only be turned on or off beforehand. The "● Record" button is a separate feature: you start and stop it manually at any time, and it keeps recording indefinitely until you stop it.

Starting a recording briefly raises the target window to the front once. If the target window moves or is resized while recording, the capture keeps following it. Recording files are saved by default as a numbered sequence like frame_00001.png under ~/Pictures/EnduranceTestGUI_Screenshots/recording_<timestamp>/. If the target app exits or crashes mid-recording and its window can no longer be found, the recording stops safely on its own (this never crashes EnduranceTestGUI itself).

The save location can be changed
"Change recording/crash artifacts folder..." in the "File" menu lets you move the folder both this continuous recording and the crash-time auto-save described in the next section use, to any other drive or folder with more free space, at any time. Use "Choose Folder..." to pick a new location, or "Reset to Default" to go back to the default ~/Pictures/EnduranceTestGUI_Screenshots/ (files already recorded/saved before the change are not moved). If recordings or crash artifacts fail to save because the destination disk is full, use this to switch to a location with room to write.
If another window comes to the front during recording, it will appear in those frames
Each frame is captured the same way as the existing screenshot feature: it's a pixel-for-pixel capture of whatever is actually visible on screen. The target window is only raised to the front once, at the start of recording — it isn't kept pinned on top for the whole duration (doing so would make the "■ Stop recording" button itself unclickable). So if another window, including EnduranceTestGUI's own, overlaps the target while recording, that window will show up in the frames captured during the overlap.

Stopping a recording brings up a "Convert this recording to an animation?" confirmation. Choosing "Yes" opens the export dialog directly, and you can also open it at any later time for any past recording folder (including ones from earlier sessions) via the "Convert Recording to Animation..." button in the log area.

In the export dialog, choose the output format and frame interval (default 500 ms), then click "Export...": a save-location dialog appears, followed by conversion with a progress bar (cancel at any time with "Cancel"). GIF is always available as an output format, using a self-contained encoder with no external tool required. MP4/WebM are only enabled when ffmpeg is installed on the machine running the app (otherwise those options are greyed out, with a hint explaining why). If the target window was resized mid-recording and frames therefore differ in size, they are automatically padded to the largest frame's size before conversion, so no content is cropped out.

Clicks and drag-and-drops performed during an endurance run are automatically marked on the recorded frames. A click/double-click draws as a fading, expanding red ring (blue for a right click); a drag draws as an orange arrow from its start point to its end point — each marker stays visible for a short time around the moment the action actually happened. This makes it possible to see where a run's fast, randomized operations actually landed just by watching the exported animation afterward.

10Crash detection & re-testing

When the target app's process is detected as gone, the run stops immediately and a dialog like the following appears.

Both the dialog and the log show which step was running when the crash was detected, how many actions had run so far, and the RNG seed. At the same time, a JSON snapshot of the test settings (with that seed), a screenshot of the operation region, a recording of the recent screen (if enabled), and the location of the OS's crash dump (if found) are all saved automatically under ~/Pictures/EnduranceTestGUI_Screenshots/ by default (or wherever you've redirected it to via the "File" menu — see section 9).

You can re-test with the same setup right after a crash
The ② step configuration, ① operation regions, and timing settings stay exactly as they were on screen even after a crash. Once you relaunch the target app, ①'s target list refreshes automatically and re-selects the app with the same name on its own. Just click "Start" to begin re-testing with the same configuration.

11Saving & loading test settings

"Save Test Settings..." in the "File" menu saves the operation regions, step configuration, and timing settings assembled in ①② together into a JSON file. "Load Test Settings..." loads it back and, if the app it was targeting when saved is currently running, automatically selects it again (otherwise a message prompts you to pick it manually). This lets the same configuration be reused across sessions or across different builds, without rebuilding it from scratch each time.

12Switching the display language

Choose "日本語" or "English" from the "言語 / Language" menu in the menu bar. Your choice is saved and takes effect from the next launch onward (the currently running window doesn't switch live).

13Troubleshooting

Clicking "Start" fails with a safety-check error

Check that the target window isn't covered by another window and isn't minimized. If that doesn't help, some environments (particularly certain tiling window managers on Linux) don't support the mechanism used to confirm the target app can be operated safely at all.

The target app doesn't appear in the window list

Click the "Update" button in ① to re-scan. Only normal top-level windows are listed.

Right-click menu item selection isn't working well / "Press dialog button" can't find the button

These are experimental features that rely on macOS/Linux accessibility support. On Linux, the target app's toolkit needs to have its AT-SPI bridge enabled (GTK/Qt apps usually have this on by default). They also won't work if the Linux desktop environment itself doesn't provide an AT-SPI D-Bus session bus (some minimal setups don't).
